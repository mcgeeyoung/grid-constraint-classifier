Capacity & realized performance: data shape

For "available capacity" and "performance score" we need both a listed side (what's enrolled) and a realized side (what actually showed up). Mocked for the demo, but the shape shapes every view.

A. Scalar listed capacity + per-event realized (simple)recommended

Each device has one kW rating (on dominion_devices). Realized performance is aggregated per event (average kW delivered).

ALTER TABLE dominion_devices ADD COLUMN listed_capacity_kw NUMERIC(10,2);

CREATE TABLE dominion_dispatch_events (
  id SERIAL PRIMARY KEY,
  ingestion_run_id INT,
  device_id_external TEXT,
  start_utc, end_utc, duration_hours INT,
  has_mandatory BOOL,                     -- contains any extreme hour
  avg_program_signal NUMERIC(5,3),          -- from dispatch table
  listed_capacity_kw_avg NUMERIC(10,2),
  realized_capacity_kw_avg NUMERIC(10,2),
  performance_pct NUMERIC(5,2)  -- realized / listed
);

Pros

One row per device per event. Performance score is one column. Easy to aggregate by zone, roll up to fleet. Mock realized by injecting ~70-90% of listed with some jitter.

Cons

No intra-event shape (can't show "device ramped down at hour 3, back up at hour 4"). Fine for demo; extendable later.

B. Time-varying capacity + per-hour telemetry (richer)

Capacity can vary by hour (battery SOC, thermostat availability). Realized is per-hour kW from DER telemetry, aggregated to events for reporting.

CREATE TABLE dominion_device_capacity (
  device_id_external TEXT, effective_from, effective_to,
  curve_type TEXT,     -- 'constant' | 'tod' | 'piecewise'
  curve_json JSONB
);

CREATE TABLE dominion_device_telemetry (
  device_id_external TEXT,
  interval_start_utc TIMESTAMPTZ,
  listed_kw NUMERIC(10,2),
  realized_kw NUMERIC(10,2)
);

-- Events table is now a view over telemetry × dispatch tiers

Pros

Matches real telemetry feeds. Unlocks charts of realized-vs-signal throughout an event. Future-proof.

Cons

More data to mock convincingly. Event-level views have to aggregate on read. Adds one full table + one lookup table.

A

Scalar + per-event (simple)

Good for the demo. Listed is one kW number per device; realized is one number per event.

B

Time-varying + per-hour telemetry

Richer. Enables intra-event charts of listed vs realized by hour.

C

Hybrid: scalar listed, per-hour realized

Listed capacity is a single kW on each device (constant). Realized is per-hour (mocked). Gives intra-event charts without the complexity of time-varying listed capacity.
