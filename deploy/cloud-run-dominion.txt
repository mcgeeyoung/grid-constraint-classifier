Dominion demo API on Google Cloud Run
======================================

For Cloud SQL creation, laptop Alembic via Auth Proxy, and dominion_devices seed SQL, see:
  deploy/cloud-sql-postgres-setup.txt

Prereqs
-------
- gcloud installed and authenticated; project selected.
- Postgres reachable from Cloud Run (Cloud SQL recommended in the same region).
- Alembic migrations already applied to that database (alembic upgrade head from your laptop).
- dominion_devices seeded so dispatch rebuild has rows to join.
- wcgrid GitHub deploy token stored in Secret Manager as `wcgrid-gh-token`
  (see "wcgrid token setup" below); Cloud Build needs it to install the
  private wcgrid package during the image build.
- DATABASE_URL and PJM_SUBSCRIPTION_KEY stored in Secret Manager as
  `dominion-db-url` and `pjm-key` respectively.

Why Cloud Run fits
------------------
- HTTPS URL out of the box for the FastAPI app and /api/v1/dominion/*.
- Scales to zero between demos (lower cost).
- Dockerfile in repo root listens on $PORT (Cloud Run sets PORT, often 8080).

wcgrid token setup
------------------
The backend depends on wcgrid which is private. Cloud Build reads a
GitHub fine-grained PAT from Secret Manager and streams it into the
docker build via BuildKit's --mount=type=secret so the token never
lands in any image layer.

1. Create a fine-grained PAT at
   https://github.com/settings/personal-access-tokens/new:
   - Resource owner: wattcarbon
   - Repository access: select wattcarbon/wcgrid only
   - Repository permissions: Contents: Read
   - Expiration: 90 days (set a calendar reminder to rotate)
2. Store it in Secret Manager:
     echo -n "github_pat_..." | gcloud secrets create wcgrid-gh-token --data-file=-
3. Let the Cloud Build service account read it:
     PROJECT_NUMBER=$(gcloud projects describe wattcarbon-internal --format='value(projectNumber)')
     gcloud secrets add-iam-policy-binding wcgrid-gh-token \
         --member="serviceAccount:${PROJECT_NUMBER}@cloudbuild.gserviceaccount.com" \
         --role="roles/secretmanager.secretAccessor"
4. When the PAT rotates, add a new version:
     echo -n "github_pat_new..." | gcloud secrets versions add wcgrid-gh-token --data-file=-
   cloudbuild.yaml references `:latest`, so no other change needed.

First deploy (build via cloudbuild.yaml)
----------------------------------------
From grid-constraint-classifier (repo root):

  gcloud builds submit --config=cloudbuild.yaml

That runs the steps in cloudbuild.yaml: build with the wcgrid token,
push to Artifact Registry, and roll a new Cloud Run revision wired to
Cloud SQL + the dominion-db-url + pjm-key secrets.

Notes on the cloudbuild.yaml
----------------------------
- The previous `gcloud run deploy --source .` flow doesn't surface the
  BuildKit secret mount we need for the wcgrid install, hence the move
  to cloudbuild.yaml + `gcloud builds submit`.
- Defaults assume PROJECT_ID=wattcarbon-internal, REGION=us-central1,
  SERVICE=dominion-api, REPO=dominion-api,
  DB_INSTANCE=wattcarbon-internal:us-central1:dominion-demo-db.
  Override with `--substitutions=_KEY=value,...` on the submit call.
- For anything except a throwaway demo, secrets stay in Secret Manager
  (already the pattern in cloudbuild.yaml's `--set-secrets`).

Cloud SQL (typical pattern)
---------------------------
1. Create a Cloud SQL for PostgreSQL instance (same region as Cloud Run).
2. Create database + user; run Alembic against it once from your laptop (or Cloud Shell) with
   a temporary authorized network or Cloud SQL Auth Proxy.
3. Enable the Cloud SQL Admin API.
4. Deploy with:

     --add-cloudsql-instances PROJECT:REGION:INSTANCE

   and DATABASE_URL using the /cloudsql/PROJECT:REGION:INSTANCE Unix socket (see Cloud SQL docs
   for the exact SQLAlchemy URL your driver expects).

5. Grant the Cloud Run default service account (or the one you use) the role
   roles/cloudsql.client on the instance.

After deploy
------------
- gcloud prints the service URL, e.g. https://dominion-api-xxxxx-uc.a.run.app
- Test: https://.../health
- Test: https://.../api/v1/dominion/ingestion-runs
- Point the GCS static demo at: https://.../api/v1/dominion (see deploy/dominion-gcs.txt and
  deploy/upload-dominion-demo-gcs.sh).

Redeploy after code changes
---------------------------
Same `gcloud builds submit --config=cloudbuild.yaml` command from the
repo root; Cloud Build rebuilds the image and Cloud Run rolls a new
revision automatically.

Optional hardening (later)
--------------------------
- Remove --allow-unauthenticated and use IAM / identity-aware access.
- Min instances > 0 only if you need to avoid cold starts for a live pitch.
